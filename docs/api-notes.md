# Как устроен API личного кабинета

Личный кабинет — приложение на Nuxt поверх JSON API. Разбирать HTML не нужно.
Всё описанное ниже снято с фронтенда кабинета и подтверждено живыми запросами.

Базовый адрес: `https://my.ranepa.ru/lk/n-api/`

## Защита от ботов

Запрос без правдоподобного `User-Agent` получает `403 Forbidden` с телом
`Forbidden / Transaction ID: …` и заголовком `content-type: text/plain`.

Это первое, обо что разбивается наивный клиент, и ломается он молча: 403 легко
принять за неверный пароль. В коде эти случаи разведены — `BlockedError` против
`AuthError` (см. `app/ranepa/client.py`).

Вне России вход дополнительно требует капчу. Практический вывод: сервис должен
работать с российского адреса.

## Вход

```
POST auth/login
Content-Type: multipart/form-data

login=…
password=…
remember_me=true
```

Ответ содержит `access_token`, `refresh_token` и `exp`. Дальнейшие запросы идут
с заголовком `Authorization: Bearer <access_token>`.

Продление — без пароля:

```
POST auth/refresh
{"refresh_token": "…"}
```

Отсюда следует важное для безопасности: **пароль пользователя хранить не
обязательно**, достаточно refresh-токена. При утечке базы это разница между
«скомпрометирован учебный аккаунт» и «скомпрометирован пароль, который человек
использует ещё в пяти местах».

Прочее из того же семейства: `auth/test` (проверка токена), `auth/logout`,
`o-auth/authorize`.

## Расписание

```
GET schedule
  uid_org=7923e704-99aa-11e5-bed4-c48508aa74e4
  type=group
  branch_type=main
  filter[]=<uid группы>      — повторяется для каждой группы
  dates[]=2026-09-04T00:00:00.000  — повторяется для каждого дня
```

Ключевое: **дни перечисляются по одному**, диапазона нет. Кабинет не ограничивает
глубину выборки — интерфейс показывает неделю просто потому, что так свёрстан.
Сколько дней запрашивать, решаем мы, и ограничение здесь этическое: не грузить
чужой сервер сильнее необходимого.

`uid_org` у головной организации фиксированный; у филиалов свой, он приходит в
профиле. Групп у студента может быть много — в наблюдаемом случае их 23.

Смежные эндпоинты: `schedule/lms-link` (ссылка на СДО), `schedule/search-group`,
`schedule/search-lecturer`.

### Схема ответа

Снята с живого ответа (30 дней, 66 пар). Обезличенный образец — в
`tests/fixtures/schedule_response.json`.

```
{
  "uid_org": "…",
  "days": [
    {
      "date": "2026-09-23T00:00:00",
      "discs": [
        {
          "start_date": "2026-09-23T15:40:00",
          "end_date":   "2026-09-23T17:00:00",
          "disc":     "Математический анализ",
          "type":     "Практические занятия",       // или «Лекционные занятия»
          "lecturer": "Фамилия Имя Отчество",
          "room":     "5 - 122 (22) П+ПК (Вернадского, 82 - корпус 5)",
          "lms_link": null,                          // ссылка на СДО у дистанта
          "groups":   {"<uid>": "ПИ-101", …},        // группы, которым читают пару
          "status":   "Добавление",  "comment": null,
          "uid_status", "uid_room", "uid_disc", "uid_type", "uid_lecturer",
          "sam_login", "sam_email"                   // персональные данные преподавателя
        }
      ]
    }
  ],
  "clientVersion": 1,
  "bitrix": "schedule/get"
}
```

Что из этого следует:

- **Дни приходят вперемешку**, не по порядку. Пустой день присутствует в
  ответе с `discs: []` — это «пар нет», а не «данных нет».
- **Признака отмены нет.** `status` во всех 66 парах — «Добавление», `comment`
  везде `null`, и фронтенд кабинета эти поля не читает (проверено по коду
  чанка страницы). Отменённая пара просто исчезает из выдачи. Отмену и перенос
  вычисляет диффер по разнице с предыдущим снапшотом.
- **Аудитория и адрес — одна строка**, адрес в последних скобках. Скобки
  встречаются и внутри — «(22)» это вместимость. Варианты: «Уточняется» (пока
  без аудитории), «СДО - СДО / дистанционно (…)» (дистант, обычно с `lms_link`).
- **Время наивное, московское**: `2026-09-23T15:40:00` без пояса.
- **Идентификатора пары нет** — есть `uid_disc`, `uid_lecturer`, `uid_room`,
  но они не уникальны для занятия. UID события в календаре считается от даты,
  времени и предмета.
- **`sam_login` и `sam_email`** — служебные данные преподавателя. В модель не
  переносятся, чтобы не оказаться ни в базе, ни в календаре.
- Часовое время `days[].date` всегда `T00:00:00`.

## Сеть: два источника с противоположными требованиями

У сервиса два внешних адресата, и им нужны разные маршруты:

| Адресат | Требование | Что будет иначе |
|---|---|---|
| `my.ranepa.ru` | российский адрес, **без** прокси | капча на входе, 403 от WAF |
| `api.telegram.org` | из России — **через** прокси | `Cannot connect to host api.telegram.org:443` |

Практические следствия, проверенные на живой машине:

- Telegram ходит через `TELEGRAM_PROXY`; для aiogram это требует пакет
  `aiohttp-socks` (уже в зависимостях).
- Клиент кабинета создаётся с `trust_env=False`: иначе httpx подхватит
  `HTTPS_PROXY` из окружения и уведёт запросы к кабинету за границу.
- aiohttp, в отличие от httpx и curl, переменные окружения с прокси
  **не читает** — поэтому «curl работает, а бот нет» это не ошибка кода.
- Даже через прокси Telegram отвечает с перебоями: примерно один запрос из
  пяти обрывается на TLS. Бот повторяет сетевые вызовы на старте, а не падает.

## Что ещё не выяснено

- **Срок жизни refresh-токена** — как часто придётся просить пользователя войти
  заново. Выяснится только наблюдением.
- **Как выглядит перенос.** В ответе нет ни отмен, ни переносов; предполагается,
  что перенесённая пара приходит как новая запись с другим временем, а старая
  исчезает. Подтвердится на первом реальном переносе в течение семестра.
- **Доступность кабинета.** В день разведки он несколько раз отдавал 502 и
  отвечал на `schedule` десятками секунд — ретраи и снапшот-фолбэк здесь не
  перестраховка.
